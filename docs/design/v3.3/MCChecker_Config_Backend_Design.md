## 1. 设计决定

配置文件是管理入口。每份配置有一条跨软件版本的版本基线主线，每台机台在该配置下有自己的保存记录；机台页面通过统一机台身份汇集多个配置文件。软件版本、原始文件版本、版本基线记录和机台记录是不同对象，不能仅凭同名或排序推断关系。

日常操作是“编辑 → 核对保存”。核对页展示目标、差异、来源和保存说明，一次保存产生不可变记录并更新当前指针。提交评审是可选协作路径；只有明确启用多人评审策略的目标，才要求另一名合格管理员批准。管理员与访客两档能力保留，不因增加评审而引入新角色体系。

所有正式保存均需并发检查、幂等回执和审计。历史只读，恢复先生成草稿，再经相同核对保存流程产生新记录。来源更新只生成候选或草稿，不自动成为版本基线、不自动修改所有机台，也不代表已下发物理设备。

本轮优先复用现有 Python 服务、原生 JavaScript 和 JSON 存储。先修正提交一致性、统一机台身份和真实来源，再补齐评审、来源识别与多视图；不把换数据库、换框架或接入 Git 服务设为前提。

## 3. 身份、版本与历史模型

W/P 指工作区与配置集，所有查询、计划、缓存及写入都必须携带并验证这两个范围。来源设置当前按工作区管理，应用候选时还需明确目标配置集。全局身份和权限配置不随工作区复制。

| 对象 | 现有或目标标识 | 约束 |
| --- | --- | --- |
| 逻辑配置文件 | `config_id`，已有 | 版本主线、参数身份、机台分支的容器；名称和磁盘路径不是主键 |
| 原始文件与内容版本 | `file_id` / `version_id`，已有 | 文件被删除后同名重传可能是新身份；内容哈希用于校验，不替代业务身份 |
| 软件版本 | `release_id`，已有 | 前驱显式引用；新增版本不静默继承旧版实际值 |
| 参数 | `parameter_id`，已有 | 配置内稳定；重命名、路径调整和属性变化不换 ID。跨文件同名不自动视为同一参数 |
| 版本基线记录 | `baseline_id` / Bn，已有 | Bn 在配置内连续，保存后不可变；按软件版本的最新记录是查询结果或可重建索引 |
| 文件内机台记录 | `machine_id` / `revision_id` / rn，已有 | 保留旧 ID 与引用；记录包含精确软件版本、采用的标准及定义 |
| 跨文件机台 | `device_id`，拟新增 | W/P 内统一身份；通过显式绑定关联 `config_id + machine_id`，一个文件在一台机台上默认只有一个当前分支 |
| 草稿与计划 | `draft_id` / `plan_id`，已有并扩展 | 可变状态带版本号；来源、目标及内容指纹绑定，不能复用旧预览提交新内容 |
| 评审与提交内容 | `change_id` / `patchset_id`，拟新增 | 每次提交内容固定；批准针对具体内容及目标，不是对可变草稿的永久许可 |

### 跨软件版本的主线

保留现有全配置主线，而不是为每个软件版本另建互不相干的“主线”。每次 Bn 保存记录其 `release_id`、前一主线记录、实际编辑起点和采用来源。选择旧软件版本时，界面读取该版本最新保存记录，不能把全局最新 Bn 冒充该版本标准。

继续保留 `parent_id` 兼容读取，并新增必要的 `parents[]`、`based_on_revision_id`、`merge_base_revision_id` 和来源引用。主线先后顺序、软件版本前驱、参数内容来源是三种关系。跨版本从旧记录生成新内容时必须保留真实起点，不能仅凭“前一个 Bn”认定三方合并共同来源。图中的连线只来自真实引用。

### 初始快照与 D0

界面中的“初始参数”只表示确实取得的软件原始数据。记录原始文件版本、来源、内容哈希、解析器版本、映射和提取时间；无法证明来源的历史数据显示“来源未知”。手工填写标准并保存，不会自动获得原始数据身份。

内部兼容 `default_revision_id` / canonical D0，并优先通过 `initial_revision_id()` 获取可展示的初始快照。旧客户端契约保留；不能给所有历史 D0 补写虚构来源，也不能为填满页面而复制 Bn 当作初始快照。

### 参数完整性

保存完整区分 `membership`（本版未引入、存在、移除）、`enabled`、`value_state`（未填写、空值、有值）以及 `intent`（继承、覆盖、固定）。`0`、`false`、空字符串与未填写不同；值相等也不意味着意图相同。采用标准更新时，固定值仍保持固定。

数字按已有 [config_values.py](../../../app/core/config_values.py) 契约保留精确文本/类型，前端不得通过通用 `Number()` 往返转换小数或大整数。每次保存绑定不可变定义版本，旧记录的名称、路径、类型、单位和属性按当时定义展示。JSON/XML/INI 的输出映射继续复用现有导出器，未映射字段、XML 注释和处理指令按现有保留契约处理；不能用简单重建对象替换模板写回。

## 4. 保存的一致性与并发

CAS 指“仅当服务器上的版本仍与编辑开始时一致，才接受本次写入”。保存请求应绑定 W/P、目标配置/机台、草稿版本、目标当前记录、定义版本以及参与本次操作的来源/模板指纹。提交前服务端重新校验；失配返回结构化 409，保留用户修改并支持按字段核对，不能静默覆盖。

单个逻辑配置的保存需要一次一致公布：不可变记录、当前指针、完整变更事件和幂等回执要么共同可见，要么都不被视为已提交。当前原子替换 `catalog.json` 并不能使随后独立更新的 `events.json` 自动具有相同保证。

建议新增薄的 V3 提交层，参考 [config_repository.py](../../../app/core/config_repository.py)“先写不可变对象、最后公布权威 state”的现有经验，但保持 V3 独立存储与旧域只读边界。具体落盘结构需在 T02 的故障实验后冻结：快照/事件/回执先以事务 ID 暂存，校验哈希与引用，再原子替换权威提交指针；读者和回执查询只承认已被该指针引用的事务。不要把“回执已写到磁盘”误认作业务已生效。

现有 `catalog.json` 可先作为兼容读取源；高增长的不可变快照和事件逐步外置，目录保留轻量索引。迁移阶段只允许一个权威写入路径，不能让旧 catalog 写入和新提交层同时各自生效。未提交对象可隔离后回收，损坏引用必须报错而不是当空数据继续运行。

`request_id` 与规范化请求摘要绑定。同一 ID、同一请求重复提交返回同一保存记录；同一 ID、不同内容明确冲突。异常、进程终止和磁盘写失败需在关键落盘阶段注入验证。沿用当前支持的进程模型，不把进程内锁描述成多进程或多主部署保障。

这一提交边界是单个逻辑配置的保存，不承诺机台多个配置文件一次原子生效。多文件操作记录每个文件的结果、尚未执行项和可重试项；如果将来确有跨文件原子要求，应单独设计事务边界及部署语义。

## 5. 编辑、评审与合并

### 日常保存

管理员从当前标准或机台已保存记录进入编辑；历史记录仅可查看、比较、导出或“以此创建草稿”。修改暂存在草稿，核对页只展示真实差异及目标。无差异时不制造空记录；保存说明不替代结构化差异。保存成功显示新记录与时间，刷新多个视图使用同一记录 ID。

访客保留已有查看能力；所有写入由服务端检查权限。下载/生成导出的权限继续沿用已有边界，不能仅靠按钮隐藏推断是否获准。

### 可选协作评审

普通目标可以直接保存，也可选择“提交评审”。提出评审后冻结提交内容：参数定义/值差异、目标、起点、来源和策略版本。后续修改产生新 `patchset_id`，旧评论保留并标明所属内容；涉及改动的批准失效。目标记录前进时重新核对、重算差异，并重新评审需要变化的提交。

评论锚定参数 ID、字段、提交内容及前后哈希；参数更名后仍能定位，删除后保留历史位置。讨论支持未解决、已解决和已过时，修改/撤回保留记录。只有实际走评审流程且策略声明需要处理的讨论，才阻止批准或保存。

管理员显式启用独立评审策略后，受保护目标的所有写 API 都检查批准，禁止通过普通保存接口绕过。另一名批准者必须有可区分的服务端主体标识；现有 [auth.py](../../../app/services/auth.py) / [authz.py](../../../app/services/authz.py) 是基于既有身份配置的两档权限，不能把可编辑显示名当作身份凭证。共享身份无法证明独立性时，先解决主体区分，不能宣称已实现独立批准或不可抵赖审计。

### 三方合并

继续使用原来源、当前目标、新来源三方比较。来源和目标均为精确记录，计划保存共同起点、定义、哈希和目标草稿版本。值冲突、删除与编辑冲突、类型/单位不兼容、更名映射歧义、继承意图变化分别处理。没有可信共同起点时只能先做两方比较或由用户明确指定真实起点，不能伪造自动合并。

合并计划持久化在 W/P 内，包含每项决议和过期条件，重启后可恢复。提交计划时再次检查所有引用，只生成草稿；随后仍走核对保存，或用户选定的评审路径。最终合并记录保留双方父引用和逐项决议；未改变字段沿用真实来源，手工解决字段记本次解决者。

## 6. 网页链接与多格式更新

生产链路复用已有的下载、解析、候选、核对及应用能力。新增的是“识别来源”的前段，而不是另外创建一条绕过校验的写入通道。既有来源种类 `http_file`、`sda_catalog`、`sda_table`、`sda_file` 继续可用；已保存来源保持原语义。

| 用户提供的内容 | 自动识别建议 | 人工补充与边界 |
| --- | --- | --- |
| 单文件地址 | HTTP 响应、文件名、内容嗅探和真实解析联合判断 | 用户确认目标配置与字段映射；登录 HTML 不得算作配置文件 |
| 普通网页 | 有界提取可见下载链接、名称、版本线索；展示发现依据 | 可选择链接、设置有限分页；未知结构进入人工规则，不能宣称任意网页均可识别 |
| JSON / XML 清单 | 识别列表及名称、地址、版本字段候选 | 用户指定受限字段路径；JSON Pointer / 有界 XML 路径，不执行任意脚本 |
| 压缩包 | 复用 [bundle.py](../../../app/core/bundle.py) 的 ZIP、gzip、TAR、TAR.GZ 处理 | 成员筛选、相对路径、目标映射与重复检测；保留旧 keyword 同时筛选/裁剪文件名的兼容语义 |
| SDA 或登录站点 | 选择已配置连接与采集适配器，读取实际目录 | 复用 collector 的登录与保活；浏览器能力不存在时明确说明，不借用用户浏览器会话 |
| 拼接下载链接 | 显示声明变量、编码后的结果与试取结果 | 限定协议和字段，敏感信息引用凭据存储；不允许任意代码、命令或自定义脚本 |

识别返回“可使用、需确认、需要登录、未识别”等可解释状态和证据，不展示未经测量的识别准确率。高级规则默认折叠；发现字段错误时自动展开并定位。试取不保存来源，不改文件，也不更新正式新鲜度。URL、变量、选择器或映射改变后，旧试取结果立即失效。

多文件更新先固定本次发现清单，再将每项映射到具体配置。先检查所有文件类型、目标碰撞、解析与映射，生成带源内容哈希的候选清单；网络失败、解析失败和无变化分别列出。每个候选仍使用“原来源文件 / 当前草稿 / 新来源文件”，不能用任意当前记录替换已丢失的原来源。源文件引用不存在时明确未知，要求逐项决议。

默认全选或“全部匹配”必须写明范围；不能静默丢弃坏文件后提示全成功。用户可明确选择有效子集，系统保存选择清单与排除原因。应用是逐配置独立保存，支持幂等重试和失败恢复；调度器可以发现更新，不能自动批准配置变更。

外部请求沿用 [downloader.py](../../../app/core/downloader.py) 的受控 HTTP(S) 与重定向校验。内网是本产品实际场景，保留显式允许的内网地址；每次重定向、解析后的目标及最终下载都要受同一政策检查。DNS 解析与实际连接间的边界需专门验证，不能仅凭 URL 字符串校验宣称全部关闭。

生产解析需设下载大小、解压后大小、成员数、深度、超时和重复名称限制，拒绝路径逃逸、符号链接越界、加密或不支持格式，并限制 XML DTD/外部实体。原始 URL、Cookie、认证头、响应体中的秘密不能进入前端日志或审计摘要。原型简化解析器与样例地址不构成这些生产能力的验收证据。

## 7. 操作记录、恢复与查看来源

操作记录面向用户先呈现“谁在何时对哪个文件/机台做了什么”，详情再显示请求、来源、差异与相关记录。保存、定义编辑、来源配置、候选决议、评审批准、恢复、导出均有对应事件；失败、拒绝和取消作为独立操作结果，不能伪装成已提交记录。

成功事件与保存同一事务公布，包含事件 ID、W/P、配置/机台、服务端主体、当时显示名与角色、时间/时区、请求 ID、操作、目标、旧/新记录、定义和来源引用。保留旧事件原文与旧身份快照，无法补证的字段显示未知。事件内容脱敏；仅提供必要摘要，完整原始文件由受控引用访问。

“查看来源”实现字段级 blame：参数名称、类型、单位、属性、成员状态、值和继承方式分别指向最后一次真实改变该字段的记录。合并接受未改内容时显示原修改者，并可展开看到本次采用者；手工解决冲突归于解决者。导入参数既记录上游文件，也记录导入/保存操作者。不能把整份文件最近保存人当作每个参数的作者。

恢复先显示被恢复记录与当前差异，生成可审查草稿，再通过正常保存流程增加新记录。不得改写历史记录、倒退整个主线计数或声称物理机台已降级。遗失主体、来源文件或旧定义时，呈现可用证据与缺失项，禁止补造。

哈希和引用检查可以发现内容不一致，不能据此宣称抵抗拥有文件系统管理权限的人篡改。合规签名、远端审计保管和强身份认证均不在本次默认范围内。

## 8. 三种视图、性能与导出

文件页默认展示参数表，保存记录以列表为主；关系图按需打开。机台页通过 `device_id` 显示所有绑定配置文件、各自软件版本、采用的基线、当前记录和待处理状态。参数页选择一个或多个稳定参数 ID，并选择有限的保存记录列，查看名称、属性和值的变化。三个入口共享相同 ID、定义、差异与来源查询，不复制三份业务状态。

服务端在分页前完成权限、范围、搜索和筛选；返回明确总数、稳定排序与查询数据版本。界面只渲染当前行/列窗口，目录和详情按需展开，长历史按游标或稳定分页加载。不得先把所有参数、所有机台及所有历史序列化进浏览器，再把前端切页当作规模解决方案。

选择模型区分“本页 N 项”“已选 N 项”“全部匹配 M 项”。显式 ID 集合与“筛选条件 + 数据版本 + 排除项”是两种不同选择；跨页保留用 ID，不用行号。切换 W/P 清除选择与未提交计划；筛选变化后解释保留或重置范围，执行前服务端重新核对数量与目标。多参数矩阵限制请求的记录列数并提供横向窗口，不允许构造无界笛卡尔积。

性能验收覆盖至少 3000 个参数，并组合多文件、多机台、长历史和重名/重命名数据。先在同一环境测当前版本，再测改造版，记录冷/热加载、首批可见数据、可交互时间、查询 p50/p95、DOM 数、长任务、内存、请求体积和服务端解析/读取次数。采用真实脱敏样本和注明规模的合成样本；阈值由基线和使用环境确定。本轮没有生产性能实测，不给出毫秒级承诺。现有 [performance_v3.py](../../../tests/performance_v3.py) 可作入口，历史脚本中已有预算不等于本轮达标。

单文件导出固定保存记录、模板、映射和输出哈希；修改输入即废弃旧预览。原始文件下载与按配置生成新文件分别显示。机台多文件导出建议 ZIP 加 `manifest.json`：列出 W/P、机台 ID、每项配置/原始文件 ID、软件版本、保存记录、采用基线、模板版本、相对输出路径、大小和 SHA-256，以及导出时间。打包开始固定这些引用，即使随后有新保存，也不混入新版本。

导出前检测同名和路径碰撞；某项失败时显示具体文件与原因，默认不交付冒充完整的包。用户明确导出子集时，清单列出未包含项。配置包表示管理系统记录的组合，不表示这些文件已同时部署到物理机台。

## 9. 增量接口与模块边界

以下是拟定能力契约，不表示目前已注册这些路由。优先扩展 [api_v3_config.py](../../../app/server/api_v3_config.py)、[api_v3_plans.py](../../../app/server/api_v3_plans.py)、[api_v3_events.py](../../../app/server/api_v3_events.py) 与现有来源 API，避免建立第二套同义端点。

| 能力 | 必须绑定的输入 | 返回与失效条件 |
| --- | --- | --- |
| 核对保存/正式保存 | 目标、草稿版本、当前记录、定义、请求 ID | 固定差异/凭据；目标或内容改变后重新核对；正式结果含记录与审计 ID |
| 多参数查询 | 参数 ID、精确记录 ID、分页/列窗口、范围 | 使用各记录历史定义；未知参数/缺失记录明确标注 |
| 机台文件查询 | `device_id`、W/P、筛选 | 明确绑定与精确记录；未确认的同名机台不合并 |
| 合并计划与决议 | 原始起点、当前目标、新来源、版本 | 持久计划、逐项决议、冲突计数；任何依赖过期拒绝提交 |
| 可选评审与评论 | 提交内容、目标、评论锚点、策略版本 | 可读状态与批准证据；不接受过期内容批准 |
| 来源识别与试取 | 链接或规则、连接引用、限额、输入版本 | 候选文件、识别依据、错误；无业务写入副作用 |
| 更新批次应用 | 固定清单、目标映射、每项候选/草稿版本 | 每文件状态、结果记录、可重试项；不假装跨文件原子成功 |
| 字段来源与多文件导出 | 参数/字段/记录或固定文件清单 | 可解释来源链或固定 manifest；不可解析引用明确失败 |

新增模块仅围绕真正缺口：V3 提交层、跨文件机台索引、持久评审与计划、来源识别规则。现有算法、解析器、鉴权与导出器继续是单一实现。依赖评估只在实现需要新组件时开展，优先复用现有标准库；不提前引入 Git 服务、数据库集群或通用抓取框架。

## 10. 迁移与回退

迁移先使用 [inspect_v3_workspace.py](../../../scripts/inspect_v3_workspace.py)、[backup_v3.py](../../../scripts/backup_v3.py) 和 [migrate_v3.py](../../../scripts/migrate_v3.py) 的现有入口，扩展只读盘点与 dry-run。列出 W/P、配置、文件、记录、引用、旧机台编号碰撞、未知来源和无法解析项，备份后校验清单与哈希。

新增结构采用显式 schema 版本。旧不可变记录和 ID 保持不变，不给旧记录补造批准、来源或作者；可重建索引与真实历史分开存。机台绑定先给出候选，只有确定唯一或经管理员确认的映射才生效；同编号跨配置并不自动证明是同一台设备。

先让读取适配新旧记录，再对选定工作区切换到一个权威写入路径。一次迁移可重入，失败有阶段标记，重新启动不会重复生成保存记录或审计。比较迁移前后快照、差异、导出字节/语义及权限结果，确认无丢失后再扩大范围。

回退先关闭新写入并保存新格式期间产生的数据与回执。不能把旧备份覆盖到仍有新保存的数据上；需要明确兼容读取或受控重放方案。旧版本无法解释的新评审、机台绑定或新记录应保留并报告，不静默丢弃。具体执行命令、备份路径及恢复演练在生产实施时写入部署手册，本轮不操作生产数据。
