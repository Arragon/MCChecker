## B2 · 实现方自裁的错误口径 —— **部分闭合，见 B7（我此前的论证不够）**

`core/reviewing.apply_edits` 对「loc 能定位到、但该节点不承载值」的情况（空叶子元素 `<empty/>`、容器元素、根元素）抛 `REVIEW_CONFLICT`，理由是 §6.7 第 6 步的三条校验（结构不变、差异集合相等、逐个比验证望值）在这种情况下会全部放行 —— 无值节点没有「原值」可比，给它写值等于凭空新增内容，而那三条断言只防「改动扩散」不防「无中生有」。

**闭合依据**：`app/services/review.py::submit` 第 30 行是

```python
current = nodes["v"][i]
if current is None:
    raise AppError(INVALID_INPUT, "只能对有值的节点提交建议", field="loc")
```

即**无值节点在提交建议阶段就被 400 拦下**。而建议是 `edits` 的唯一来源（`apply_edits` 只被审阅提交路径调用），所以该 `REVIEW_CONFLICT` 分支在生产链路上**不可达**，是纵深防御而非用户可见行为。

两处错误码不同（提交 400 vs 写回 409）**不是不一致**：400 面向用户、带 `field="loc"` 让前端定位到输入框；409 是内部兜底，触发即意味着上游逻辑已经破了，不该伪装成用户可修的字段错误。维持现状。

**遗留动作（很小）**：卡 1 的 PR 描述与完成证据注释里写明「`v is None` 的那类节点走不到写回」，作为兜底保留。

**⚠ 我这条闭合论证的边界（评审指出，我已确认）**：`services/review.py:88-94` 只拦 `v is None` 的节点。而「元素里有注释/PI」时，compact 显示的是**有值**的（`v='5'`），提交阶段不会 400，但 `apply_edits` 定位不到 ⇒ 那条「生产不可达」只对**真空节点**成立，**对 B7 不成立**。别再拿 B2 当全局免死金牌。

## B3 · 标准库重写会丢 prolog/epilog —— **已修复于 `9684661`，待复查确认**

XML 声明之外、根元素之外的内容（根外注释、`<?xml-stylesheet href="…"?>`、文档尾随文本）在 `ET` 解析后重建时**会静默丢失**。§6.7 第 6 步的校验只比较**有值节点**，因此这类丢失不会触发 `REVIEW_UNSAFE` —— 也就是说会产出一份「业务语义正确但少了 prolog 内容」的文件。

实现方刻意**没有**加注释/PI 计数守卫，理由：属性值里可能合法含 `<!--` 字样，计数比对会误伤正常审阅。

**为什么搁置**：真正的修法是把 prolog/epilog **原样搬运**（在 `tostring` 结果前后拼回源文本的对应区段），而不是加校验拒绝。这是本卡范围内的改进，但需要单独一组用例与实现，且要确认现有样本里是否存在带 prolog 内容的真实文件 —— 若不存在，属 §17 的已知限制更合适。

**评审已实测复现三种丢失，且都"报告成功"**：`<?xml version="1.0"?><!-- header --><R><a>1</a></R>` 改 `a` → 根前注释消失、无错误；`<?xml-stylesheet href="a.xsl"?>` → PI 消失、无错误；`<R><a>1</a></R><!-- trailer -->` → 根后注释消失、无错误。同一函数对 DTD 是明确拒绝的（`reviewing.py:273-276`，理由正是"第 6 步看不见这个丢失"），所以这不是范围边界而是**疏漏**，且新加的 docstring 声称"业务语义由第 6 步校验兜底"是过度承诺。**处置从"记录限制"改为"必修"**：把源的 prolog/epilog 字节原位拼回（B3 原本倾向的方案）。

**已做的量测（2026-10-17）及其结论：不足以判定严重度**（够不够成 Critical 要看真实语料）。 真实 `data/` 里只有 **1 个** XML 配置文件，实测无根外注释、无 `<? ?>` PI、无根元素后的尾随文本。**单样本不能证明生产语料里没有**，所以「频率为 0」这个分支不能被本机数据支撑。

**恢复后的动作**：
1. 由了解真实语料的人回答一个二选一：生产配置文件里是否存在「根外注释 / `<?xml-stylesheet?>` 之类的 PI / 根后的尾随文本」？
2. 若**不存在** → 记入 SPEC §17 已知限制（§17 已经列了「标准库 XML 重写改变格式（引号、空元素、实体）」这一条，prolog/epilog 丢失是同一根因的更严重表现，应合并进同一条并升级描述），UI 帮助文案补一句，本卡不动。
3. 若**存在或不确定** → **另开一张卡**做 prolog/epilog 原样搬运（属 `apply_edits` 的正确性，不是校验），同时处理引号/空元素统一写法的 diff 噪声。不要顺手加进卡 1，会让已通过的 70 条用例面临重写。
4. 注意严重程度不对称：引号统一只是 diff 噪声；**prolog 丢失是内容缺失**，若真实文件依赖 `<?xml-stylesheet?>` 或根外注释承载信息，生成文件会静默少东西，而语义校验会判定通过。若走到第 3 步，优先级应按「正确性缺陷」而非「格式瑕疵」定。

## B7 · 元素内含注释/PI 时，显示为有值的节点永远写不回去 —— **已修复于 `9684661`，遗留见 B8**

评审实测复现（本 checkout）：

- `<R><a><!-- c -->5</a></R>`：compact 显示 `/R[1]/a[1]` 的值为 `'5'`，但 `apply_edits` 报 `REVIEW_CONFLICT 无法唯一定位：/R[1]/a[1]`。
- `<R><a><?pi?>5</a></R>`：同上。
- `<R><a>5<!-- c -->6</a></R>`：compact 显示 `'56'`，改成 `"9"` 后输出 `<a>9<!-- c -->6</a>` 再解析成 `"96"` → `REVIEW_UNSAFE 写回后的值与建议值不一致`。

**根因**：两处解析口径不同。`apply_edits` 用 `insert_comments=True` 解析，元素文本只从 `elem.text` 取（`reviewing.py:341-348`）；而显示链路的解析树丢掉注释/PI 子节点（`parser.py:508`），标准库 `TreeBuilder.text()` 会把被丢弃节点前后的文本块**拼进 `.text`**（`parser.py:612-613`），所以显示的 `'5'` / `'56'` 与写入侧看到的 `elem.text`（`None` / `'5'`）不是同一个东西。

**为什么这条比 B2 严重**：它是**可达**的。`services/review.py:88-94` 只拦 `v is None` 的节点，这类节点显示有值、提交建议会通过，然后 M3-02 的 `/review/submit` 永久 409「无法唯一定位」，而前端给出的补救是刷新 —— 刷新完值还在、还是定位不到，用户死循环。**故障是安全侧的（没写坏数据），但等于该文件对该节点不可审阅，且错误信息误导。**

**修法（评审给的，我认可）**：写入侧按显示链路同样口径算"有效文本"（`elem.text` 加上前面被丢弃的注释/PI 兄弟节点之后的尾随文本），并跨该跨度写值；或者明确拒绝这类元素并给一条**独立**的、不说"无法定位"的消息，同时记入限制。三种输入都要补测试。

**归谁做**：卡 1 的修复轮（同一函数、同一根因，拆开做只会让卡 2 在未修的地基上开工）。

## B11 · 2026-10-18 21:00 UTC · 已合并代码里有一条**间歇性失败的用例**（控制方当场复现 3/20）

**发现方式**：M4-02 安全卡补登记写接口时，实现代理报备 `tests/test_scheduler.py::test_reinit_stops_the_previous_thread_before_starting_the_next` 是"既有负载型抖动"，并称本树与 pristine 各 2/40 失败、与它的改动无关。控制方没有采信这个比例，当场在同一棵树里**只跑那一条用例**连跑 20 次：**3 次失败**。也就是说这不是罕见环境噪声，而是每跑五六次就红一次。

**失败形态（捕获到的原文）**：

```
>       assert _sched_threads() == [scheduler_module.THREAD_NAME], "同一进程只许留一条调度线程"
E       AssertionError: 同一进程只许留一条调度线程
E       assert ['mcsched', 'mcsched'] == ['mcsched']
```

**机制判断**：这条用例在 `stop()` 之后**立刻**要求系统里只剩一条调度线程。但 `stop()` 置的是停止位，线程要等自己从睡眠里醒过来才退出——所以"旧线程已经消失"是一个异步结果，被当成同步事实断言了。用例前面那两条顺序断言（`start()` 被调时旧实例的 `stopping` 已置位）是**同步且稳定**的，也正是这条卡真正要保护的不变量（不许同时有两条线程各投一份定时任务）。

**因此要分清两件事**：① 断言写错（把异步收敛当即时成立）——这是测试缺陷；② 产品里旧线程退出有多慢、这段时间是否真的可能投出第二份任务——这是实现问题，本轮**没有结论**。当前证据只支持①，不足以支持②，也不允许把②说成"已排除"。

**待办（另开 chore 卡，不在任何功能卡里顺手改）**：把这条用例改成**有界等待**（对旧线程 `join(timeout)`，超时无论多久都判失败而不是立刻判失败），并在报告里给出旧线程实际退出耗时；如果测出来退出时间达到一个调度周期量级，就要回头查实现（两条线程都活着的窗口里，`_active`/互斥表能不能挡住双份提交）。**验收要求**：改完后连跑 40 次零失败，且拔真防护仍能变红——不许改成"等 5 秒后随便什么状态都算过"。

**更正我上面那句"每跑五六次就红一次"——它只在特定负载下成立（控制方自己复核后修正）。**
两次测量的事实：① 早先那次是在**别的代理同时跑全量测试**的机器负载下，用 `-k reinit` 连跑 20 次，红 3 次；② 稍后在同样代码上用完整节点 id 连跑 40 次，**红 0 次**（`runs=40 failed=0`）。也就是说这条用例的失败是**负载敏感**的：高负载下会红，安静时测不出来。

这不改变结论，但改变了严重性的说法：**它不是随机高频坏，而是"负载一来就坏"的竞态**——一个依赖线程真退出的时序断言，恰恰在机器忙的时候最容易红。安静环境下 0/40 也**不能当作"没这回事"**：竞态存在与否取决于断言的形状，不取决于我这次抽到了几次红。修法仍是**有界等待 + 在负载下验收**（要求修复卡在人为制造并发负载的情况下连跑 40 次零失败，而不是安静跑一遍就宣布稳定）。

另外更正一处我自己写错的东西：我给评审者用的用例标识缺了类名 `TestSingleton::`，照原文跑收集数为 0、退出码 4。完整可跑的节点 id 是 `tests/test_scheduler.py::TestSingleton::test_reinit_stops_the_previous_thread_before_starting_the_next`。

## B13 · 2026-10-19 04:02 UTC · 严重教训：我给中断代理代打的「保全提交」**把一把被拔掉的 CSRF 闸门提交进了历史**（`9626072`，已推远端）

也就是**全站写接口的跨站请求伪造检查被短路**。我没看出来就把它整片 `git add` 成保全提交并推到远端。该分支上原样跑全量会得 `39 failed / 1318 passed`（接手代理实测），所以这道闸门在**那次工作区状态下是被拔掉的**，只是从没人跑过。

**当前状态**：接手代理已还原，分支 tip `aab1b19` 的 `app/server/http.py` 与已合并版本 **逐字节相同**（`git diff` 为空），全仓再扫 `MUTATION|if False and` 零命中。**没有任何一处把这个坏状态合并进集成分支**；受影响的是 `mc-v2/m3-13-ip-admins` 的**历史**里留着一个禁用安全控制的提交。

**因此立三条规矩（这才是这条的价值）**：
1. **代打保全提交前必须先扫破坏痕迹**：`MUTATION`、`if False`、`assert True`、`@pytest.mark.skip/xfail`、被改成常量的判定、被注释掉的守卫调用。本项目每个实现代理都会做变异实验，中断**很可能**发生在"实验现场还没还原"的那一刻——这与我此前踩过的"未提交工作会被冲掉"是同一个中断的两种坏结果，防了后者不等于防了前者。
2. **保全提交信息里要点名"可能含实验现场"**，并把 SHA 记进台账（就是本节），让后续任何人**不得 cherry-pick 该提交**、不得只看分支历史就断定安全控制有效。
3. **合并判断只看 tip 与工作区，不看历史**：PR 的 diff（tip vs 集成分支）才是被合并的东西；本例里 diff 对 `http.py` 为空，所以危险没有进入产物。但要在接手词里显式要求还原并复测，否则人会去找那个坏提交。
