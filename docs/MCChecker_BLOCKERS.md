## B2 · 实现方自裁的错误口径，待评审/产品确认

`core/reviewing.apply_edits` 对「loc 能定位到、但该节点不承载值」的情况（空叶子元素 `<empty/>`、容器元素、根元素）统一抛 `REVIEW_CONFLICT`。实现方给出的理由：这三条语义校验（结构不变、差异集合相等、逐个比验证望值）在这种情况下会**全部放行** —— 因为没有「原值」可比，写值等于凭空新增节点，而节点总数与 `t` 序列的断言只防「改动扩散」不防「无中生有」。

**为什么搁置**：这是设计判断而非明显缺陷，且 §6.7 第 5 步只写了 `#text` 与元素自身值两条路径，没有规定空叶子元素算不算可写目标。规范在这里是沉默的。

**恢复后的动作**：查 `services/review.py::submit` 第 3 步「节点无值 → 400」的既有口径 —— 如果提交建议阶段就已经拦住了无值节点，那么 `apply_edits` 的这个分支在真实链路上不可达，属**纵深防御**，维持现状即可，只需在卡 1 的 PR 描述里写明「此分支在生产链路上不可达，作为兜底」。若两处口径不一致（一处 400 一处 409），则统一为 §7.1 的错误码表并同 PR 改 SPEC。

## B3 · 标准库重写会丢 prolog/epilog，语义校验看不见

XML 声明之外、根元素之外的内容（根外注释、`<?xml-stylesheet href="…"?>`、文档尾随文本）在 `ET` 解析后重建时**会静默丢失**。§6.7 第 6 步的校验只比较**有值节点**，因此这类丢失不会触发 `REVIEW_UNSAFE` —— 也就是说会产出一份「业务语义正确但少了 prolog 内容」的文件。

实现方刻意**没有**加注释/PI 计数守卫，理由：属性值里可能合法含 `<!--` 字样，计数比对会误伤正常审阅。

**为什么搁置**：真正的修法是把 prolog/epilog **原样搬运**（在 `tostring` 结果前后拼回源文本的对应区段），而不是加校验拒绝。这是本卡范围内的改进，但需要单独一组用例与实现，且要确认现有样本里是否存在带 prolog 内容的真实文件 —— 若不存在，属 §17 的已知限制更合适。

**恢复后的动作**：
1. 先量一次真实数据：`grep -c` 统计 `data/profiles/*/configs/*.xml` 里根外注释与 `<?` PI 的出现频率（注意 `data/` 未被 git 跟踪，只能在真实工作区测）。
2. 若频率为 0 → 记入 SPEC §17 已知限制，UI 帮助文案补一句，本卡不动。
3. 若频率非 0 → **另开一张卡**做 prolog/epilog 原样搬运（属 `apply_edits` 的正确性，不是校验），并在该卡同时处理引号/空元素统一写法的 diff 噪声问题。不要顺手加进卡 1，会让已通过的 70 条用例面临重写。
