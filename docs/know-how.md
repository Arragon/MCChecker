# Project Know-How

> v2 已移除 `MC.caps`/`WIRED`/`WIRED_SETTINGS`/`MC.unwired*` 与 NiceGUI；下文提到这些机制或旧页面的条目仅作历史参考，不要照旧流程改代码。

## 1. Common Problems
- NiceGUI 的 `ui.tree` 组件需要特定的数据格式，需将解析结果转换为 `{id, label, children}` 结构
- XML 属性需在树形视图中特殊处理，作为 `@attr_name` 子节点展示
- NiceGUI 标签页管理需手动维护状态，使用定时器刷新 UI
- APScheduler 在 NiceGUI 中需要正确初始化，避免重复创建 scheduler
- 版本对比时文件名前缀会导致路径不匹配，需要归一化路径后再比较
- DL 反解里 `trans_coeff == 0.0` 是 **validate 放行但会除零** 的配置（M3-10 / INH-1895）：`dltool._scale_of` 对 `pp_energy` 返回 `trans_coeff / power_conv_coeff`，而 `validate` 只拒绝 `power_conv_coeff == 0.0`，所以换算系数 `s` 可以合法地等于 `0.0`；`reverse` 的 `y / s` 对**任意** y（含 `0.0`，Python 浮点除零不产出 inf/nan）抛 `ZeroDivisionError`，`multi_check` 在 `y_min`/`y_max` 任一非 None 时同样抛（两者都 None 时走观测域，不崩），`forward` 是乘 `s` 所以只是全 0。责任归 **M3-11（`app/services/dl.py`）**：把它翻成 400，或出 spec 让 `validate` 拒绝 `trans_coeff=0`；`dltool` 是纯 core、还没有调用方，不在这里兜底也不在这里加 HTTP。现状哨兵是 `tests/test_dltool_multi.py::TestTransCoeffZeroDividesByS`（钉「validate 返回空串 + 这两处抛」，M3-11 改行为时它会红）。`dlmath.js` 同样不拒绝 `trans_coeff=0`，但那边算出 `Infinity`/`NaN` 继续跑——两边只差在「谁响亮失败」。
- DL 服务层的三条不变式（M3-11 / INH-1896 首轮评审）：① `GET /dl` 的 `rev` 与 `items` 必须在同一把 `storage.profile_lock(pid)` 内读（`ThreadingHTTPServer` 下 GET/PUT 并发，两次读之间插入保存会返回「旧 items + 新 rev」，客户端拿新 rev 再 PUT 就覆盖别人的保存）；② `PUT /dl/{item}` 的 body 按 §7.11 是完整 item，四个范围键缺一个就 400（`_validated_params` 把缺失与显式 null 都归一成 None，放行缺失会静默清空磁盘值；`name`/`binding` 缺失却是保留磁盘值）；③ mock 的数值转换必须按 Python `float()` 语法（`Number("")===0`、`Number([])===0`、`Number([5])===5`、`Number("0x10")===16`，后端分别是 invalid/400），且 PUT 先校验 body 再比 rev、缺 `If-Match` 的 409 要带 `detail.header`。

## 2. Proven Solutions
- 树形视图使用 ui.expansion 替代 ui.tree，可实现在节点旁添加自定义组件（如收藏星标），ui.tree 的 add_slot 方式与 NiceGUI 事件系统集成较复杂
- 返回导航使用历史栈（session_tab_history list），每次切换标签页时将当前页面压栈，返回时弹出栈顶
- 收藏星标使用 ui.icon 组件，通过修改 _props["name"] 和 _props["color"] 切换 star/star_outline 和颜色，然后调用 update() 刷新
- "部署者"和IP显示已从界面移除，is_deployer() 仅用于功能权限判断（管理按钮可见性等）
- 使用递归函数将 XML/JSON 统一转换为树形结构
- 使用 IP 地址判断部署者权限，127.0.0.1 和服务端本机 IP 视为部署者
- 更新源回读可以是单个 XML/JSON，也可以是 zip、tar 或 gzip。压缩包只取出其中的 `.xml`/`.json`（不落盘、不跟符号链接）。映射上的可选 `keyword` 是正则：在文件名去掉扩展名后搜索，命中则保存为「匹配文本（有捕获组时用第 1 组）+ 小写扩展名」。`MachineConstant` 把 `Default_MachineConstant_basics.xml` 收成 `MachineConstant.xml`。没关键词时，单个文件仍用更新源自己的文件名，压缩包按包内原名加入。加密包、解压超过下载上限、切削后重名都会拒绝。
- 人员与管理员名单全机型共用 `data/ip_mapping.json` 与 `data/admin_users.json`，读写用 `storage.people_write()`，不要再写进 `profiles/<pid>/`。旧的按机型副本只在全局文件还不存在时合并一次（同一 IP 保留 `updated_at` 较新的那条），合并后不删除机型目录里的旧文件。`/revision` 仍会打开这两份身份文件，路径在数据根而不是机型目录。
- 文件版本归档使用日期后缀: `filename_20260524.xml`，若已存在则精确到秒
- 版本对比使用 difflib.unified_diff 生成文本差异，结构化差异使用归一化路径匹配
- 会话级标签页状态使用 Python 列表+字典在渲染函数闭包中维护
- 审阅写回要在原文上保住根元素之外的内容（M3-01 / B3）：`ET` 的事件里没有位置信息，位置只能自己用 `xml.parsers.expat` 量（`CurrentByteIndex`）。三个坑：① `ParserCreate()` 必须**关掉命名空间处理**，expat 文档写明开启后该偏移不保证对应原始字节；② 根元素有两种收尾，`</名称>` 的偏移落在 `<` 上、自闭合 `<a/>` 的偏移已在 `/>` 之后，判据用「偏移处是不是 `</`」，不能「往后找第一个 `>`」（`<R><a/></R>` 会在根结束之前就撞上 `/>`）；③ 区间两端要按字节核对，而 UTF-16 下 `<`/`>` 各占两字节，marker 得跟着编码换。
- `ET.register_namespace` 改的是**进程级**的 `xml.etree.ElementTree._namespace_map`，注册只增不减，没有公开 API 能读回原值。不要在请求路径上「序列化前后快照/恢复」它：FastAPI 的同步端点跑在线程池里，两个并发写回会互相踩——A 的 `tostring` 可能读到 B 刚恢复进去的映射。每次写回都先把**当前文档自己的**前缀登记进去，所以同一份原文在同一进程内产出一致；别的文档留下的条目只会多不会少（str→str，量级可忽略），并发下最坏情况是前缀拼写换一种写法，`loc`/值/节点数都不变，第 6 步校验与 `to_compact` 的显示标签都不受影响。因此 `apply_edits` 的 docstring 明确写着它不是纯函数。
- 同一份 XML 用两种口径解析会得到不同的 `.text`（M3-01 / B7）：显示链路 `insert_comments=False` 时，标准库把被丢弃的注释/PI 前后的字符数据**拼进** `elem.text`；写入侧 `insert_comments=True` 时同一段文本被切成 `elem.text` + 各注释/PI 兄弟的 `.tail`。所以「元素的有效文本」必须自己算（`elem.text` 加上首个子元素之前那些注释/PI 的 tail），写入也要跨这一整段跨度写，否则会出现「界面显示有值、提交建议被接受、写回永久 `REVIEW_CONFLICT 无法唯一定位`」这种用户刷不出去的死循环。
- 审阅分组只认 `group_key = locator or node_path or node_key`，不要用 `storage.list_review_items`（M3-02）：它按 `(source_file, node_key or node_path)` 分组，而 v2 建议按 §5.2 写 `node_key=""`，于是会退化成按旧节点 ID 并组——同名兄弟共享旧 ID，「item 第 1 个」和「item 第 2 个」的建议被并成一组，批准其中一条会把另一条连带驳回，写回还可能指错节点（正是 v1 的根因）。分组只能在 service 层自己算，原始条目仍可以复用 `storage.load_edit_remarks()`。
- 审阅的「能不能通过」必须列表与提交共用一份定位算法（M3-02）：`views/review.js` 只用 `n.stale || !n.resolvable` 两个布尔决定按钮是否可点，服务端另算一套就会出现「按钮能点、点下去 400/409」的死路。legacy（无 `locator`）建议按旧 ID 试匹配，**恰好 1 个**匹配才 `resolvable=true`；`legacy` 只用于打徽标。另外当前文件解析不了或被删时仍要给出真实 `current_sha`（拿不到就 `null`），否则前端只能带空 `source_sha` 提交，连「驳回」这条唯一出路都会被 409 挡死。
- 审阅写回的落盘顺序（M3-02）：`apply_edits`（内含 §6.7 第 6 步的再解析比对）必须在生成文件与状态更新**之前**跑完，这样「校验失败 422 不写任何文件、不改任何建议状态」是靠顺序保证的，不需要回滚；幂等表落在独立的 `profiles/<pid>/review_idempotency.json`（10 分钟窗口、**不**进 `COPY_PROFILE_FILES`），塞进 `edit_remarks.json` 顶层会破坏 §5.2「现有字段不变」。
- 更新源的「内容变没变」只认 `storage.save_config_file_detailed` 返回的 `unchanged`（M3-05 / R5）：它在机型锁内读旧字节、逐字节相同就**不写不归档**并返回 `unchanged=True`。调用方再自己比一次 sha256 会得出两套「变没变」，`revision.bump(pid, "files")` 就会在文件字节没变时通知全部客户端刷新。§10.2 第 6 步要求的锁内重读比的是另一件事——**比较基准（当前内容）没被并发换掉**，不是「新内容是否等于当前内容」；两者都要有，措辞别混。
- 根节点指纹可以从已经解析好的 compact 文档里拿，不必再解析一遍（M3-05）：XML 的根元素是 `nodes["id"][1]`，形如 `root/<原始 tag>`（命名空间写作 `{uri}local`），去掉固定前缀 `root/` 就是可比较的 tag——用它而不是 `nodes["l"][1]`（显示标签），因为换一种前缀写法（`a:root` → `root`）显示标签会变、根节点却没变，会把好更新误判成「下载到了错误页面」。JSON 的根类型（object/array）compact 文档里**没有**（合成根的 `t` 恒为 `"json"`，空容器更是没有子节点可推），只能自己 `json.loads` 再 `isinstance`——别用「第一个子节点的标签长什么样」去猜。
- 服务层那段 `except ValueError → 400 + WARNING`（`updates.rename_source`）仍在，但**它兜的已经不是文件名字符集**：`storage._sanitize_config_filename` 自 N1（INH-1912）起委托 `fsutil.validate_filename`，抛的是 `AppError(INVALID_INPUT)`，所以这个分支现在只兜「下载链接不能为空」等仍会抛裸 `ValueError` 的校验。仍然有效的两条教训：① 翻译时只用 `except ValueError` 包住整个调用，会把净化内部别的 `ValueError` 一起掩成「用户文件名写错了」，必须带上原消息并 `logger.warning` 一条；② 历史成因记此，字符集唯一真源见下一条。
- 后台任务的「进度可见性」只能靠**带通知的容器**拿到，不要指望任务函数自觉上报（M3-07）：§10.1 规定 `fn` 用 `task.progress[...]` 与 `task.result["items"].append()` 更新，而卡 5 的 `updates._publish()` 正是这么直接写的——它不调任何回调，也不该被改成调。所以 `services/tasks.py::Task` 把这两个字段做成 dict/list 的浅子类，写入时回调 runner 递增 `tasks`；去重键是 `(done, total, 条数)`，同一个值写第二次不算变化，否则无意义的递增会把别人的刷新提示刷成噪声。浅子类不影响 `json.dumps` 与 `==` 普通 dict/list 的既有断言。
- 任务结束时 runner **只补 `settings`，绝不补 `files`**（M3-07 与 R5 的接缝）：`files` 由 `updates.update_source` 在「字节真的变了」时递增一次，runner 无从判断有没有变，再递增一次就是虚假通知（unchanged 的更新会惊动全部客户端）。`update_all` 写 `schedule.json.last_run` 而卡 5 已裁定自己不递增 `settings`，那一份由 `FINISH_PARTS` 补。抛异常的失败任务两类业务分量都不补（失败写不递增），但 `tasks` 必须补，否则别人的界面永远停在「进行中」。**卡 9 的 `refresh_records` 不许照这一句往表里加 `files`**（本条旧写法「要加就改这张表」是错的，M3-09 修复轮已推翻）：`_finish` 对条目状态是 `download_failed`/`skipped`/`not_found` 的任务照样传 `error=None` 并无条件走 `FINISH_PARTS`，进了表就是给每一次「拉到 0 条新记录」发横幅；正确落点与判据见下一条 ①。
- 工作线程的 daemon 位**不能当判据**，停止顺序仍必须先排空任务再关 HTTP（M3-07 / R9，修复轮 2 更正）：`threading.Thread.__init__` 把 daemon 从**创建者**继承下去（`threading.py:828`），而 `MCServer.daemon_threads = True` 且 `submit` 是 HTTP 处理线程调的 ⇒ **现网里 `mctask_N` 工作线程就是 daemon**；只有从主线程提交（单测的形状）才是非 daemon。两种形态下解释器最后都会等它们（非 daemon 走 `threading._shutdown`，daemon 走 `concurrent.futures.thread` 注册的 `_python_exit`，实测一个卡死的下载把进程拖到 91.7 秒才退），但**该等的不是「进程别死」，而是「删锁之前它们得散」**。因此：① 停止顺序仍是 `runner.shutdown(30)` 先、`server.shutdown()` 后，且 `shutdown()` 要幂等（信号连按）；② 「还有没有人在写」只能按**线程名**数（`services/tasks.py::worker_threads`，摘掉不写盘的 `mctask-shutdown` 等待线程），第一版按 `not t.daemon` 过滤时，测试全绿而真实进程 30 秒就把锁删了、下载还在跑——是手工 SIGTERM 验证抓出来的。测试里只比对调用顺序串也测不出真隐患：让假 server 在**自己被关闭的那一刻**采样「还有几个进行中任务」并断言为 0，把两行互换这条才会红。
- 单实例锁是本应用**唯一**的跨进程写锁，所以它必须活得比**它看得见的所有任务工作线程**久（M3-07 修复轮 2 / C1 / H3；修复轮 3 把「每一个写的人」收窄成实际交付的保证，见本条文末的已知残留）：`locks.profile_lock` 是 `threading.RLock`、`write_gate` 只在进程内，跨进程谁都不挡；两个进程同时写 `data/profiles/<pid>/` 时，`update_all` 对 `schedule.json` 的读-改-写和逐文件归档会互相静默覆盖。三条机制要一起记：① `SingleInstanceLock.release()` 是无条件 `os.unlink`，它不知道有没有人还在写；② `runner.shutdown()` 那 30 秒**小于**一个卡死下载的最坏耗时（`DEFAULT_DOWNLOAD_TIMEOUT_S` 30 × `DEFAULT_DOWNLOAD_RETRIES` 3 + 退避 `(1, 2)` ≈ 93 秒，而 `updates.update_all` 还串行遍历映射项），所以「排空超时」是常态不是意外，超时后线程仍在写而端口已经释放；③ 残留锁能被下一次启动接管（`acquire()` 读 pid → `_process_alive()` 判活），删错的锁不能。**因此后续卡片绝不允许在任何超时路径上删锁**：删锁前调 `tasks.wait_for_workers(EXIT_WORKER_TIMEOUT)`（300 秒，取值的推导写在该常量的注释里），等不散就保留锁文件并记 ERROR，让进程自然把线程跑完。`tests/test_api_tasks.py::TestLockOutlivesWriters` 用「闸门不放行 + 排空预算 0.01 秒」钉住这条不变量，其中「提交方必须是 daemon 线程」那条形状是必须的——它挡住上面那个 daemon 判据的错修法。**已知残留（修复轮 3 / Item 3，未闭合、刻意不闭合）**：「每个写的人」只覆盖 `mctask` 工作线程——HTTP 处理线程是 daemon（`MCServer.daemon_threads = True`），`server.shutdown()`/`server_close()` 都不 join 它们，而 handler 对 `schedule.json`、`update_status.json`、配置映射的读-改-写只扣在进程内 `profile_lock` 下，所以理论上存在「退出的瞬间恰有一条 handler 停在 RMW 中间、锁已被删」的窗口。不当它是 C1 的第二个实例，是因为那几次写是本地短小的原子 replace（无网络 I/O、微秒到毫秒级），不是分钟级下载；真要拿到「活得比每一个写的人久」的强保证，后续卡得把这几条 handler 侧 RMW 挪进任务队列（或登记在途 handler、退出前 join 完再删锁），而不是在超时路径上碰运气。
- 调度线程（`app/services/scheduler.py`，线程名 `mcsched`）是**三道安全网都看不见的手搓 daemon 线程**，所以它只许「到点往队列里投一条 `update_all`」，绝不自己下载/落盘（M3-08 / INH-1893，卡 8 手递手 §1 的落地）：① 它不是池线程 ⇒ `concurrent.futures.thread._python_exit` 不 join 它；② `mcsched` **故意不带** `mctask` 前缀 ⇒ `tasks.worker_threads()` 那条「还有没有人在写 `data/`」的判据看不见它（把不写盘的线程塞进去只会让删锁更晚更含糊）；③ `h3_data_guard` 的盲区②就是「最后一次快照之后才落盘的线程」。三道都失明 ⇒ **泄漏与越界写入只能由本卡自己钉死**，机制有两条，改动前都要保住：(a) 观测点在文件系统而不是返回值——用例把 `os.remove` / `shutil.rmtree` / `os.replace` 全部包一层「记录 (发起线程名, 路径)」，再断言 `mcsched` 自己发起的删除只落在 `data/temporary/` 与 `profiles/<pid>/cache/doc_v2|diff_v2/`（派生数据，损坏即丢弃重建）、且 `mcsched` 一条 `os.replace` 都不发起（本仓库每一次权威 JSON 落盘的提交动作就是 `fsutil.atomic_write_bytes` 里那句 `os.replace`，比桩 `builtins.open` 覆盖面准）。**这条安全用例有两个「让它永远绿」的写法要避开**（M3-08 修复轮 Important 2）：① 允许目录**不许从被测的 `scheduler.DERIVED_CACHE_DIRNAMES` 推导**——推导出来的白名单跟着被测常量一起放宽，往那个元组里加 `"../configs"` 时它自己该抓的回归恰好抓不到，白名单必须在测试里硬编码成 `("doc_v2", "diff_v2")`（机型清单可以来自注册表，那是环境不是权限面）；② 放在候选路径旁边的权威样本**要 `os.utime` 老化到超过 TTL**——一份「刚刚写的」文件是被清理自己的年龄过滤器保住的，不老化就等于断言过滤器而不是断言代码，同一元组加 `"../configs"` 照样全绿。两条合起来才是「变异 `DERIVED_CACHE_DIRNAMES` 必红」；只做②不做①时白名单仍会跟着放宽，只做①不做②时文件仍是靠运气活下来。(b) `tests/conftest.py::isolated_scheduler` 是 autouse、显式依赖 `isolated_task_runner`（拆序＝装序的反面 ⇒ 一定在 runner 关掉、`monkeypatch` - `update_status.json` 的键就是**映射名**，所以它归改名与删除的数据生命周期管（M3-05 复审 I1–I3）：改名时键要跟着搬（`migrate_files` 只决定本地产物走不走，映射名照样改，所以状态键两种情况下都必须跟随），删除时**清除**而不是保留。不处理有三笔账：① 改名后 `GET /sources` 的 `last_result` 恒为 `null`，UC-31 的「状态列」在改名那一刻失真；② 旧键成为永久孤儿（文件只增不减）；③ 最坏的一种——`DELETE` 之后用同一个名字重新 `POST`，新源直接继承上一个同名源的「最近结果」，显示一条从未发生在它身上的更新。删除选「清除」正是因为第三笔账。§7.9 的迁移清单没点这个文件名（它是新增文件，不在 v1 里），而 `storage.update_config_mapping` 也**不**搬它（storage 不知道它），调用方必须自己补这一步。
- 「锁外读 + 锁内写」是 `storage` 这套「每个 `save_*` 自锁」接口最容易拼错的形状（M3-05 复审 I1/I2）：`load_schedule()` 与 `save_schedule()`、`load_update_status()` 与 `save_update_status()` 各自只锁住自己那一步，分两次加锁地拼起来就是 §5.4 要防的丢失更新——`update_all` 写 `schedule.json.last_run` 期间进来的 `PUT /schedule`（卡 7 的部署者设置）会被这次读到的旧副本整份覆盖，落在**用户配置**上；`update_status.json` 的合并同理，两个并发完成的结果会互相丢项。修法是把整段读-改-写包进**一次** `storage.profile_write(pid)`：`locks.profile_lock` 返回 per-pid **RLock**，`save_*` 内部再取一次同名锁只是重入，无死锁（`create_source` 从一开始就是这个形状，照它来）。闸门那一半也同理：`locks.WriteGate.write()` 是**计数器**（`enter_write` 只把 `_writers += 1`），不是排他锁——它只负责「维护态之前等一下在途写入」，串行化全靠那把 RLock，所以嵌套两层 `profile_write` 不会自己把自己锁住（卡 8 的 `PUT /schedule` 实测这个嵌套形状：外层包 RMW、内层是 `save_schedule` 自锁）。

## 4. Testing Notes
- 使用 pytest 运行测试，`pytest tests/ -v`
- Python 3.9 兼容性不能只靠 `compileall`：函数注解里的 `X | None` 能编译，但在导入时求值才报 `TypeError`。验证方式是用 3.9 解释器实际导入模块（`python3.9 -c "import app.core.storage"`）；当前 v1.0.1 的 `storage.py`、`differ.py`、`dltool.py` 在 3.9.11 下导入即失败。
- 前端模板（`app/web/`）的纯逻辑测试：**脚本化验收命令钉死为 HTTP 形态**（M3-06 第三轮 C1，`file://` 那一形态已作废，理由见下一条）——从 `/tmp` 起一个只服务 `app/web/` 的临时静态服务器（随机端口，**绝不要**拿仓库 `data/` 当服务根，用完关掉），然后
  `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu --no-sandbox --virtual-time-budget=8000 --dump-dom "http://127.0.0.1:<port>/tests/index.html"`，检查 `<title>ALL PASSED (n)</title>`。人工调试仍然可以直接用浏览器打开 `app/web/tests/index.html`。
  **HTTP 形态有两种「必须重跑、不许读成判决」的抖动**（第三轮实测；根因是 `--virtual-time-budget` 与真实网络延迟竞速——预算到点时还有脚本在途，Chrome 会取消它们）：① dump 早于 `report()` ⇒ 标题停在初始「MCChecker 前端单元测试」，既不是绿也不是红（就是下面 F2.4 那条「什么都没有」）；② dump 早于某个外部 `.js` 执行完 ⇒ 那个文件的符号缺失，一批用例**同时**报 `MC.views.settings is not a function` / `MC.openImport is not a function`。②长得很像真回归，但它不是：逐字节核过服务端交付（并发 2 下 80/80 与磁盘文件 sha256 一致，stdlib 与 keep-alive 两台都是），而且安静机器上不复现。**实测抖动率按服务器形态排**：手搓 `ThreadingHTTPServer` + HTTP/1.1 keep-alive 22 次 **0 次**异常；stdlib `python -m http.server`（HTTP/1.0，每请求一条连接）24 次里 5 次（4 次①＋1 次②）；手搓单线程 `socketserver.TCPServer` 9 次里 2 次。⇒ **验收优先用 keep-alive 的多线程服务器**（`docs/know-how.md` 第 4 节这条命令就是），profile 共用与否不是变量（一次性 `--user-data-dir` 照样抖过），抬预算也不保证（20000 在同一窗口里仍抖出 1 次①）。**判据只认 `ALL PASSED (n)` / `n FAILED / m`**：看到①或②一律重跑，既不许当绿、也不许去改代码。`file://` 从来不出这两种（本地读盘没有网络竞速，实测 10+ 次全确定）——那正是「为了稳退回 `file://`」的陷阱：它稳，但对再下面那条 Critical 盲区是瞎的。
- `--virtual-time-budget=8000` 就是整个页面的**全局硬截止**（M3-06 复审 F2.4）：将来任何用例只要等待超过剩余预算，Chrome 会在 `report()` 跑到之前就把 DOM dump 掉，页面报的不是红而是**什么都没有**——标题停留在初始「MCChecker 前端单元测试」，既非 ALL PASSED 也非 N FAILED，绿不绿都看不出来；给用例加长等待前先想预算账。
- **经 `MC.mock.handle` 的页面用例是按 140+random(120) 毫秒「烧预算」的，加用例前先算账**（M3-13 修复轮实测，紧接上一条那个 8000 硬截止）：本卡给 mock 契约加了一条 13 次 `handle` 调用的新用例，页面在 8000 预算下**确定地**停在「运行中…」（标题不换、`<ol>` 空、5/5 次都一样）——那不是 know-how 上面记的那两种抖动，**重跑救不回来**，是预算被真实用完了。对照实测：50 条的原 suite 在 6000 下仍绿，加到 6 次调用时只能在 7000 与 8000 之间勉强收线，收到 5 次调用后 7000 也绿（≈ 留 1 秒余量）。⇒ 覆盖面优先放 pytest 侧：`tests/utils/mock_people_crosscheck.js` **执行** mock 真身逐值核，不占页面预算；页面用例只留「mock 自己那条不对称」这类最小判据。若将来必须再加 `handle` 调用，要么先量出新的总耗时再决定，要么由控制方改钉死的预算值，不许把「什么都没有」读成绿或读成红。
- **`file://` 下「外部脚本里产生的 Promise 拒绝」永不派发，所以 `file://` 命令不能当验收**（M3-06 第三轮 C1，Chrome 155 实测；**旧文档把它归因为「串行队列进行中」是错的，别再那样写**）：真正的变量是**产生拒绝的脚本来源**，与队列在不在跑无关。同一份页面两种来源各跑一遍的实测：① `file://` + 外部脚本（`tests.js` 的全部用例与所有视图模块都属此类）⇒ `unhandledrejection` **从不派发**，队列进行中产生的不派发，改到 `report()` 跑完、队列早已 settle 之后再产生的**照样不派发**，预算 8000→30000 也一样；② `file://` + inline 页面脚本 ⇒ **会**派发，所以盲区精确到「外部脚本来源」而不是「这个页面的所有拒绝」；③ `error` 通道在 `file://` 下照常派发，只是外部脚本的 message/filename 被浏览器掩成 `Script error.`（只有 inline 的带 `filename:line`）；④ HTTP 下两个监听都完整命中、含真实来源。**后果（这就是「静默绿」的最后一层）**：某条用例把断言留在一条**它自己不 return** 的 Promise 链里，`file://` 下确定性地绿——用例注册了也启动了（`EXPECTED_CASES` 钉死满足）、没有同步抛（`error` 通道静默），唯一能抓住它的就是 rejection 通道，而那条通道在 `file://` 下是瞎的。实测对照（同一条「不 return、断言写在链里」的失败用例，钉死计数同步加一条使它不被数量闸挡住，预算同为 8000，在本卡最终树上跑）：`file://` → `<title>ALL PASSED (41)</title>` 且那条用例显示为 ✓ 通过，`http://127.0.0.1:<port>` → `<title>1 FAILED / 42</title>` 并点名那条拒绝。因此全局兜底的三层（`error` + `unhandledrejection` 监听、`EXPECTED_CASES` 用例数钉死、队尾先让出宏任务再汇总）**只有在 HTTP 命令下才闭合**；新增浮空链要么 return、要么自己 `.then(null, …)` 接住，并且生产代码里每条不返回的链都得有 rejection 分支（`shell.js::pollTasks` 的任务 refetch 就是第三轮补的那条）。

- **调度器的周期清理用例要按注入的假钟老化被测文件**（M3-13 修复轮在 `4e69a0a` 上实测）：`sweep_derived_caches(now=...)` 只认 `now_fn`，测试若用真实 `time.time()` 设置文件 mtime，文件会落在假钟之后、被当成「未来」的新鲜文件；`tests/test_scheduler.py::TestSchedulerWritesNothingAuthoritative::test_the_mcsched_thread_deletes_only_temp_and_derived_paths` 因此在主线确定性红。修法是用 `clock.now().timestamp()` 老化；这不是放宽断言，是把测试的时钟来源对齐到被测代码。
- **接手别的代理留下的「保全提交」时先跑全量、再读代码**（M3-13 实测）：那条 WIP 把 `app/server/http.py:266` 的 CSRF 判断写成了 `if False and method in WRITE_METHODS and …  # MUTATION B`——那是上一轮「证明断言能红」的变异实验残留，被保全提交原样钉进了历史，一旦当成「已合并卡现状」读过去就会漏掉一个**全站写接口无 CSRF**的洞。全量 `pytest -q` 当场 39 条红（`tests/test_api_security.py:927`、`:1079`，加上 authz/sources/tasks/schedule/favorites/remarks/review/compare/delete/http 各卡自己的那一条），所以**检测器一直存在，只是没人跑**；`grep -rn MUTATION app tests` 只是最快的点名办法，判据必须是跑出来的红。两条推论：① 已评审已合并卡的文件（`app/server/http.py`、`tests/test_api_security.py`）出现在别人 WIP 的清单里时，默认按事故处理并逐 hunk 审，`git diff <该卡的合并提交> -- <文件>` 应当是空的；② 变异实验只在同一次会话内做、当场还原，不许让它进任何一次 `git add`。
- `tests.js` 的 `EXPECTED_CASES` 闸是**可自证伪**的，所以「ALL PASSED (n)」里的 n 就是页面自己数出来的注册数（M3-13 实测）：把副本里的常量从 51 改成 47，同一份页面报 `1 FAILED / 52` 并在列表里点名「用例注册数不符：预期 47，实际注册 51」。这条探测要在**改之前的 /tmp 副本**上做，别把它当成一次真实验收轮次记进计数。

## 7. Do Not Do
- 不要在 pytest 之外直接跑临时脚本调用 `app.core.storage` / `app.services.*`：数据根重绑定只发生在 `tests/conftest.py` 的夹具里，`storage.DATA_DIR = tmp` 这类手工赋值改不到由它派生的其它常量，脚本会把样本和 `cache/doc_v2` 写进仓库真实的 `data/`。要么写成 pytest 用例（自动隔离），要么显式用 `run.py --data-dir $(mktemp -d)`。
- 不要只 `realpath` 一侧就算相对路径（`os.path.relpath(源, storage.DATA_DIR)`）：`fsutil.resolve_within()` 返回 realpath，而 `get_archive_root_dir()` / `get_records_root_dir()` 拼出来的是未解析的路径；macOS 上 `/var` 又是指向 `/private/var` 的符号链接，于是恢复区 manifest 的 `from` 会变成 `../../../../../../private/var/…` 这种没法照着放回去的废值（M2-12 真实后端跑出来才发现，pytest 的 tmp 两侧恰好一致所以没抓到）。要两侧都 `os.path.realpath()` 再 `relpath`。
- 不要把「某个调用方必须翻的安全开关」放进原语的默认值里，也不要指望它自动生效：`DownloadPolicy.block_loopback` 的默认是 `False`（卡 4 裁定，部署者要从内网更新源取配置），但 `persist=false` 的链接导入把字节放进**访客可见的临时区**，这一条必须 `True`——否则访客就能把导入指到服务器本机 `127.0.0.1` 的服务上、再从临时文件查看器把正文读走（N2 / INH-1913 补的就是这个 opt-in）。落点选在调用方自己的授权边界（`app/services/upload.py::_download`，`persist` 在那里一次性决定策略），原语继续保持默认 `False`；判据是「谁能看到落地的字节」，不是「哪个函数比较方便」。反过来在 `default_policy()` 里改成 `True` 会一起断掉部署者与调度器的内网更新源。
- 不要让下载失败的细节透出到访客能读到的响应体：`Connection refused`（端口关着）与 `HTTP 404`（端口开着、路径没有）只要文案不同，就是一只 SSRF 端口探测器。`services/upload.py` 沿用 `download_file` 的旧口径——一律收成同一句 `下载失败：连接超时或目标不可达，已重试`、`detail` 留空，原因只进日志（下载器已把 URL 脱敏成 `scheme://host/path`）。`TOO_LARGE` 是唯一例外，它必须原样上抛才有 413。证据在 `tests/test_api_import.py::TestImportUrlErrorHygiene`。
- 不要使用小众第三方库
- 不要在日志中输出敏感信息
- 不要修改用户上传的原始文件
- 不要在客户端会话中持久化服务端配置
- 不要使用 Python 3.10+ 专属语法（match, X|Y 类型联合）
- 不要在 ui.tree 上使用 add_slot 来实现自定义交互，事件处理与 NiceGUI 集成困难
- 不要一次性写入过大的文件内容到 PowerShell
- **只读路径一律不许在数据根里 `makedirs` 把骨架目录长出来（派生缓存仍然在读的时候落盘，见下）；H3 守卫的快照自 B10.2 起覆盖「目录集合」，不只是文件字节**（chore 卡 / `app/core/storage.py`）：实测链 `GET /api/v1/p/{pid}/files → storage.list_config_files() → _ensure_dirs()` 会在真实 `data/` 里长出 `profiles/<pid>/archive/`、`records/`、`cache/`、`cache/parse_tree/` 四个目录，而权威文件哈希逐条未变——旧快照（只哈希常规文件）对此完全沉默，于是「只读接口没改数据目录」这句安全主张在机制上不可验证。口径现在是：`_ensure_dirs()`（`storage.py:200`）**只许写路径调**（v2 读路径零调用；`app/` 里剩下的调用者只有 `parse_cache._get_cache_dir()`——`app/server/**` 够不到它，v1 页面 `app/pages/**` 的读经 `load_tree()` 会撞上来，本卡没动它），本模块里的四个调用点是改名迁移（`:457`）、`save_record_file`（`:616`）、`save_config_file_detailed`（`:836`）、`save_review_generated_file`（`:1577`，它经 `_reserve_file` 裸 `os.open(O_CREAT|O_EXCL)`，目录不在就先炸，属于「写确实需要」而不是防御性调用）；机型根由启动流程 `ensure_profile_layout()`（`run.py:140` 调）与复制机型的 `_copy_profile_data_locked()` 建，业务子目录由该机型**第一次需要它的写**建。`device_models.add_model()` 把目录也记成条目（键 = 归一化相对路径 **+ 结尾 `/`**，值 = 常量 `DIRECTORY_ENTRY_MARKER`，刻意不是 64 位十六进制，两类条目因此不可能互相冒充；符号链接目录不进，与「不跟随符号链接、非常规文件不哈希内容」同口径），`compare_snapshots` 里目录只走 新建/删除 两类、**不参与改名配对**（否则「删一个空目录 + 建另一个空目录」会被写成一句假改名），差异类别一条没加（`DIFF_LABELS` 仍是四份），报告靠结尾 `/` 区分目录。改口径有两个连带后果要知道：① 公告那行的「N 个文件」只能数文件——一树空目录报成「4 个文件」就是撒谎（`test_enforcing_notice_reports_files_and_dirs_separately` 钉住）；② `is_enforcing` `RUN_PROCESS_TRIAGE` 那句（先停服务再重跑，能稳定复现才说明是测试写穿了数据根），**不许**为了让它安静就把目录退回快照之外。已知残留、刻意不在本卡范围：`storage.get_record_dir()` / `get_archive_dir()` 仍带 `makedirs`，读它们的 `list_record_versions` / `list_archived_versions` / `load_archived_file` 只挂在 `app/pages/**`（M4-07 要删的旧 NiceGUI 面）上，`app/server/**` 的读接口早就绕开这两个创建型 helper（`app/services/history.py:83`、`app/services/documents.py::_count_files` `cache/` + `cache/doc_v2/` 并写缓存文件，`GET /files/{name}/archives` 与 `GET /files/{name}/records` 经 `history._cache_write()`（写在 `history.py:220`）建 `cache/` + `cache/diff_v2/` 并写缓存文件。机制都不是 `_ensure_dirs()`，而是派生缓存写走 `fsutil.atomic_write_bytes()`，它在 `fsutil.py:78` 给自己的目标目录 `makedirs`。这 4 条同一轮里**权威字节逐条哈希不变**，属于「读一次就把派生缓存建起来」的设计内行为（§5.1 把 `cache/doc_v2/`、`cache/diff_v2/` 标成可丢弃的派生数据，§6.5 第 3 `recovery._invalidate()` → `parse_cache.invalidate()` → `parse_cache._get_cache_dir()` → `storage._ensure_dirs()`（`app/core/parse_cache.py:15`）把缺失的骨架目录重新长出来——一棵只剩 `configs/` 的根上实测补出 `archive/`、`records/`、`cache/`、`cache/parse_tree/`，外加删除前备份 `recovery/<stamp>_delete_file_<pid>_<name>/`。本卡第一次把这条口径变成可判红的证据（`tests/test_readonly_paths.py`：真实 HTTP
